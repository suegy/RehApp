Living design and implementation reference. Update this document whenever a product, visual, technical, or data decision changes.

1. Current Baseline

  • The Flutter visual shell is implemented in lib/main.dart: the responsive login, language toggle, scroll-collapsing menu, notification banner, roots-style home path, compact expanding follow-up modules, and the core-module view.
  • Theme colors, typography, input/button styling, and material texture live in lib/app/app_theme.dart. UI locale files, module-list JSON, and localized Markdown content live in content/ and are loaded by lib/app/app_content.dart.
  • Login uses PocketBase email/password authentication against the configured endpoint and restores a valid SDK session token. Passwords are never persisted by the app, logged, or embedded in source; the password form controller is cleared immediately after an authentication request. The local endpoint is suitable only for development and must be replaced with HTTPS for deployment.
  • Mock/data-preview status: the home-path module states, notification, progress, core completion, questionnaires, media controls, and assignment save action are currently local visual/data previews. They do not yet read or write PocketBase records.
  • The browser build has been verified with flutter build web; static analysis and the widget test suite pass.
  • Flutter web is enabled. web/manifest.json already declares portrait-primary.
  • The primary delivery target is a mobile-phone browser in portrait orientation. The layout must remain usable when a browser permits landscape or when viewed on a larger screen.

3. Experience and Visual Direction

Decision: use a soft, optimistic, youthful visual language rather than a generic business dashboard. Pastel color, irregular friendly geometry, and a light background texture make the experience approachable while text, contrast, and controls retain accessibility.

Visual reference: VisualDesign.html is the interactive mobile-first prototype for this direction. It includes the login, home path, and core-module content view. Module content is presented as a scrollable sequence of friendly, distinct block cards for text, media, and assignments. Approve or revise it before Flutter implementation; its named color tokens map directly to the proposed Flutter theme tokens.

ElementChoice
Theme tokensDefine semantic colors, typography, spacing, radii, border shapes, and elevations in one Flutter theme file. Use an easy-reading system font stack (Verdana, Tahoma, Arial, sans-serif) for body and controls. Initial palette: pastel violet navigation/action, lilac and paper surfaces, peach and mint accents, butter attention, and dark plum text. Use material-like surface texture: soft tone-on-tone gradients, broad light falloff, and extremely faint grain aligned to the surrounding pastel. Avoid visible dots, stripes, or high-contrast decorative patterns. Cards use a white surface, border, and shadow to establish separation. Add a restrained tonal highlight to buttons without reducing label contrast. Do not hard-code these values in feature widgets.
Mobile frameSingle-column content constrained to a readable maximum width, 16-24 px horizontal padding, minimum 44 x 44 px targets, safe-area padding, and vertical scrolling. Portrait is the designed layout.
Home pathThe current module is a full-size numbered card. Following modules stay compact but descend in an alternating left-right-left sequence of balloon-like cards on a roots-inspired path, rather than sitting in a horizontal row or directly below one another. Use a mostly vertical root trunk made from restrained cubic Bezier curves; it may drift gently but must not zigzag across the path. Separate Bezier branches cross horizontally only to reach an offset child module or avoid an intervening card. A balloon expands on pointer hover, keyboard focus, or focus within to reveal its description and action. Cards use deliberately varied rounded corners, small rotation, light panel texture, dashed locked borders, offset shadows, and asymmetric border widths instead of uniform rectangular outlines. Touch interaction must expand a follow-up card on its first tap before any navigation action. The visual path must retain a linear reading and tab order.
Module flowWithin a module, ordered learning blocks remain a wide, readable single-column sequence. Alternate blocks may shift slightly left/right around a quiet vertical guide to echo the path visual without making reading order or scanability ambiguous.

Notification boxPlace below the revealed/collapsed header area. Use an icon, heading, plain language, and an optional action. It must not rely only on color and must be announced accessibly.
Language controlUse compact lowercase ISO 639-1 codes: sv and en. The selected option uses aria-pressed; each option has its full localized accessible name. This is available in the collapsed menu and login screen.
AccessibilityMeet WCAG 2.2 AA contrast, support keyboard navigation and screen readers, preserve user text scaling, label every media and form control, and provide captions/transcripts for video/audio content. Texture and decorative irregularity must never reduce legibility or communicate state alone.

4. Language Architecture

  • Use Flutter's gen_l10n with English and Swedish ARB files for all application UI strings, validation text, dates, labels, and accessibility labels.
  • Store authored module content as localized records in PocketBase, keyed by stable module and block identifiers plus locale (en, sv). Do not embed learning content as UI strings in Dart.
  • Choose the first language from the browser locale, allow users to switch language from the information/settings view, and persist the selection in the user profile. Fall back to Swedish for supplied content, then English when no selected-language translation exists.
  • Visual elements are language-aware: allow translated titles to wrap, use directional/semantic icons rather than text in images, and localize media captions, transcripts, and alt text.

5. Content Model

A module is an ordered set of typed blocks. This makes the current introduction and future modules data-managed rather than custom Flutter screens.

Editable Content Source

  • Maintain UI translations in content/locales/<locale>.json, the ordered home path in content/modules.json, and each module's authored content in content/modules/<module-key>/<locale>.md, outside lib.
  • Module IDs and locale JSON keys are stable across translations. The module list defines order, state, title key, and detail key; a translator can add or replace one Markdown file without changing Flutter code.
  • Use TODO: text only where approved content or a media reference has not been supplied. Production publishing must reject any remaining TODO marker.
  • The current Flutter visual shell reads these source assets directly. A future content-import command will validate the JSON and Markdown files and upsert them to PocketBase.
  • Add module descriptions, module-list entries, and translations by editing these content files. The accompanying content/README.md defines the authoring contract.

6. Progress and Rules

  • Every module has machine-readable prerequisite rules evaluated from the authenticated user's profile and progress records.
  • The core module is the sole exception: it is always available to a newly authenticated user.
  • Each module's state is locked, available, in_progress, or completed. The home path uses this state rather than hiding modules, so users understand what is next.
  • Personalized order must be supplied by a backend rule or an explicit ordered list on the user profile. The client renders the returned order; it must not contain undocumented clinical decision logic.
  • Define module completion explicitly per module, for example all required blocks viewed/submitted. Completion timestamps and assignment submissions are stored separately for auditability.

7. PocketBase Design

Decision: PocketBase is the system of record. The browser authenticates through its standard email/password endpoint and stores only the supported authenticated session mechanism. The password is supplied only to the authentication request, password-entry suggestions/autocorrect are disabled, and the in-memory controller is cleared after submission. PocketBase collection API rules must enforce ownership; client-side checks are not security.

CollectionPurpose and key fields
users (auth)id, email, emailVisibility, verified, name, avator, record JSON, underAgend, durgExperience, created, and updated.
modulesPer-user progression: id, user_id, content JSON, created, and updated.
module_blocksModule relation, block type, stable key, order, media file/URL, questionnaire definition, and localized content relation.
content_translationsParent kind/key, locale, title, Markdown body, media labels, transcript/caption data.
assignment_responsesUser relation, module/block relation, text response, optional audio file, submission timestamp, status.
questionnaire_responsesUser relation, module/block relation, answer JSON or child answers, submission timestamp. Keep questionnaire version/schema with each response for historical interpretation.
notificationsUser relation, localized title/body, severity, action target, active range, read/dismissed timestamp.
Security and privacy: this service processes sensitive wellbeing information. Deploy PocketBase only behind HTTPS, define least-privilege collection rules before client work, restrict uploaded file access, avoid sensitive data in logs/analytics, set retention/deletion policy, and obtain a privacy/security review before real-user release.

Development endpoint: http://127.0.0.1:8291. Set this as the initial pocketBaseUrl value near the top of lib/main.dart. A production HTTPS URL will replace it at deployment.

Test user: create test@test.se with password tester45 through a clearly named development-only PocketBase migration or seed script, excluded from production deployment. Remove that one migration/seed entry to remove the user. Never create a known-credential account from browser code or ship it in production.

Module-state collection: use the private modules collection for per-user module progression. Filter records by user_id = @request.auth.id; store each module's moduleId, state, percent, and components in its content JSON field. The components JSON uses stable component IDs: { "film-1": { "required": true, "state": "completed" } }. The app maps users.underAgend and users.durgExperience to its internal profile-filter names.

8. Proposed Flutter Architecture

  • lib/main.dart: app bootstrap and the one documented pocketBaseUrl configuration constant.
  • Feature-based structure: lib/auth/ contains the login flow, lib/learning_path/ contains the home path and navigation header, lib/module_content/ renders lesson content, and lib/shared/ holds reusable visual widgets. lib/models/, lib/data/, and lib/controllers/ provide shared state and content services without dictating feature file placement.
  • lib/app/: router, theme tokens, localization configuration, and dependency setup.
  • lib/features/auth/, home/, modules/, questionnaires/, notifications/, and settings/: feature-local screens, state, models, and repositories.
  • lib/data/pocketbase/: PocketBase client, DTOs, and repositories. Keep PocketBase fields out of presentation widgets.
  • Use the official/maintained PocketBase Dart client, a maintained Markdown renderer with explicitly configured link handling, a web-capable audio-recording package, and a media player package after package compatibility is verified against Flutter web.
  • Use declarative routing so the home, module, and information views have stable browser URLs and protected routes redirect unauthenticated visitors to login.

10. Acceptance Criteria

  • A user can log in with valid PocketBase email/password credentials, refresh the browser without an unnecessary login, and log out.
  • Changing the documented URL constant changes the PocketBase endpoint without searching through the project.
  • The menu is reachable by tap, hover, keyboard, and screen reader; it collapses without obscuring content.
  • Active notifications are visible below the menu and the full current-notification list is accessible.
  • Three path cards display in the defined snake visual arrangement while accessibility reading order remains first-to-last.
  • Locale switching changes UI and available authored content, then remains selected on the next session.
  • The core module is open for a new account, while a non-core module cannot open until its prerequisite rule evaluates true.
  • Each supported question type validates and persists an answer owned by the authenticated user.

12. Iterative Module Rules Process

  1. For each module, record its purpose, intended audience, visible title/description, required blocks, and completion definition in its source folder.
  2. Before implementing its availability, ask for the exact user facts or completed tasks that unlock it. Record approved rules as data, not implicit Flutter code.
  3. Check each new rule against sections 3, 4, 6, and 7 of this document: it must retain a clear locked-state explanation, be localizable, be accessible, protect user data, and be enforced by PocketBase rules or approved backend logic.
  4. Seed and test the rule with a representative account before releasing it. Update this document with the rule, rationale, owner, and affected module.
  5. Do not invent content or clinical progression. Until details are supplied, retain visible development placeholders and keep only the core module available.
